## 1. Как устроена экономика и торговля Polymarket

Этот раздел разбирает экономику и торговлю Polymarket на уровне, достаточном для воспроизведения механик, и в конце даёт прямой маппинг «механика Polymarket → как переносим в Legio (очки + LMSR)». Ключевая разделительная линия, которую важно держать в голове: Polymarket — это **CLOB-биржа на ончейн-коллатерале**, а Legio (по решению заказчика) — **LMSR на очках**. Часть механик Polymarket — это следствие именно его архитектуры (mint/merge, ордербук, ончейн-сеттлмент); они переносятся не «как есть», а в виде эквивалентного эффекта, который LMSR даёт «бесплатно».

### 1.1. Создание и курирование рынков

Главный контринтуитивный факт: **обычные пользователи не публикуют рынки сами**. Листинг централизован — рынки создаёт внутренняя команда («markets team»), а пользователи только *предлагают идеи* (через X, Discord-каналы `#polymarket-ideas` / `#submit-a-polymarket`). При этом **резолюция децентрализована** через UMA. Это сознательный гибрид: централизованный контроль качества формулировок + нейтральный сеттлмент.

Дисциплина формулировки: **«заголовок описывает рынок, но разрешают его только rules»**. Обязательный блок правил:

| Компонент правил | Требование |
|---|---|
| Условие YES / условие NO | Точное, измеримое, проверяемое |
| Resolution source | Один авторитетный источник (госанонсы → офиц. заявления → верифицированные API); если источник указан — валиден только он |
| Дата + время + таймзона закрытия | Обязательно с зоной (часто ET/UTC); без зоны вопрос неоднозначен |
| Крайние случаи | Перенос / отмена / ничья / недоступность источника — прописываются per-market |

Архитектура каталога — **Event → Market(s) → Outcome**:
- **Market** — всегда бинарный вопрос Yes/No со своим ордербуком; технически имеет `conditionId`, `questionId` и пару токенов (Yes/No).
- **Event** — контейнер, группирующий 1+ связанных рынков; имеет `slug`, заголовок, описание, теги, агрегированный объём.
- Два паттерна: *single-market event* (event ≈ market) и *multi-market event* (мульти-исход: каждый кандидат = отдельный бинарный рынок-строка под одним событием).

Редакционные инструменты курирования каталога (стоит скопировать в модель данных): флаги `featured`, `forceShow`, `forceHide`, `isCarousel`, плюс оптимизированные изображения (исходник + сжатая версия), теги как стабильная таксономия.

### 1.2. Outcome-токены: почему цена = вероятность и YES + NO = $1

Каждый бинарный рынок выпускает **два ERC-1155 токена** (Yes и No) на Gnosis Conditional Token Framework (CTF). Это не акции — это **условные требования**: токен платит **ровно $1**, если его исход реализовался, и **$0** иначе.

**Почему YES + NO = $1 — это гарантия контракта, а не рынка.** Механика `splitPosition` / `mergePositions`:
- **Split (mint):** заблокировал $1 коллатерала (pUSD/USDC) → контракт чеканит 1 YES + 1 NO.
- **Merge:** сжёг пару YES + NO → вернул $1 коллатерала.

Следовательно до резолюции `1 YES + 1 NO ≡ $1` в любой момент. Если на рынке YES + NO > $1 — арбитражёр сплитит за $1 и продаёт обе доли дороже; если < $1 — скупает обе и мёржит обратно в $1. Этот **встроенный арбитраж через split/merge** держит сумму цен у $1 без всякого AMM. Важно не путать: split — это механическая чеканка обоих токенов за $1, она *не связана* с рыночной ценой; «$0.50» — это лишь средняя доля доллара на токен, а не цена.

**Почему цена = вероятность.** Выигрышная доля гасится за ровно $1, проигрышная — за $0. Значит справедливая цена доли = ожидаемая выплата = `P(исход) × $1`. Отсюда цена в долларах ≈ подразумеваемая вероятность: YES = $0.65 → рынок оценивает шанс ~65%, NO = $0.35. Перевод тривиален: `цена YES × 100 = вероятность в %`.

**Redeem:** после резолюции `redeemPositions` гасит выигрышные токены 1:1 за коллатерал (100 выигрышных долей → $100), проигрышные = $0.

### 1.3. CLOB: ордербук, типы ордеров, mint/merge-матчинг, off-chain матчинг + on-chain сеттлмент

Polymarket — не AMM, а **гибридно-децентрализованная биржа** (CLOB). Архитектурный принцип:

> Ордера матчатся **off-chain** централизованным оператором (быстро, мгновенная отмена без газа), а расчёт происходит **on-chain, некастодиально** через контракт `CTFExchange`. Оператор предоставляет matching/ordering/execution, но **не может** ни ставить цены, ни исполнять несанкционированные сделки.

- Ордер = **EIP-712-подписанное сообщение** (`maker`, `makerAsset`, `takerAsset`, `makerAmount`, `takerAmount`, `baseFeeRate`). Пользователь подписывает ключом; оператор лишь сводит подписанные ордера.
- Конвейер: `Order Matched → Trade Created → Settlement Request → Exchange Contract → Atomic Transfer → Finalized`. Matching ≠ Settlement. Отмена — мгновенно off-chain; ончейн нужен только для самого сеттлмента (и пользователь может отменить ордер ончейн независимо от оператора).
- Отображаемая цена = **середина bid/ask** (`(best_bid + best_ask)/2`); если спред > $0.10 — показывается last trade price. Но реально торгуешь по ask (покупка) / bid (продажа) — спред есть стоимость входа.

**Ключевая инженерная деталь — три типа матчинга в контракте** (удваивают глубину книги):

| Тип | Кто встречается | Что делает контракт |
|---|---|---|
| **NORMAL** | продавец YES ↔ покупатель YES | переводит токены продавца покупателю, коллатерал — обратно |
| **MINT** | покупатель YES ↔ покупатель NO | берёт коллатерал у обоих, **чеканит** N сетов (YES+NO), раздаёт каждому свою сторону — новая ликвидность «из воздуха» |
| **MERGE** | продавец YES ↔ продавец NO | **мёржит** N сетов обратно в коллатерал, раздаёт деньги |

Все ордера технически лимитные; «маркет-ордер» = лимитка по marketable-цене. Типы:

| Тип | Поведение | Класс |
|---|---|---|
| **GTC** | лежит до исполнения/отмены | limit |
| **GTD** | активен до UTC-таймстампа (мин. 1 мин) | limit |
| **FOK** | исполнить целиком и сразу, иначе отменить весь | market |
| **FAK** | исполнить доступное сразу, остаток отменить | market |

UX-нюансы тикета: **BUY-market задаётся в долларах** («сколько потратить»), **SELL — в долях** (с кнопкой Max, дробные доли). Показываются «To win $X» (= доли × $1), Shares, Avg price. Tick sizes: `0.1 / 0.01 / 0.001 / 0.0001`. Минимум: $1 на market-ордер, 5 долей на limit. `price` на market-ордере работает как worst-price limit (slippage protection). Post-only — только для GTC/GTD.

### 1.4. Резолюция через UMA Optimistic Oracle

Polymarket не резолвит сам — это делает внешний **UMA Optimistic Oracle (OO)** на Polygon через адаптер `UmaCtfAdapter`. Поток:

1. **Предложение исхода.** После закрытия кто-то («proposer») предлагает исход, внося бонд **$750 USDC.e**. Reward proposer'у: исторически $2, сейчас многие рынки — $5.
2. **Окно диспутов (liveness) = 2 часа.** Если не оспорено — исход финализируется оптимистически; держатели выигрышных долей делают redeem по $1. Это путь «~2 часа» в 99% случаев.
3. **Диспут.** Оспорить может **кто угодно** (бонд = бонду proposer'а). Механика двухступенчатая:
   - **Первый диспут → автоматический `reset`** (новый раунд предложения с новым окном 2 ч) — дешёвый «второй шанс» на честную ошибку до дорогого голосования.
   - **Второй диспут → эскалация в UMA DVM** (голосование держателей $UMA, commit-reveal ~2–4 дня). Итого спорный рынок: **~4–6 дней**.
4. **Экономика бондов.** Победитель диспута возвращает свой бонд + половину бонда оппонента; проигравший теряет весь бонд.

**Кодировка исходов (ancillary data → payout-вектор CTF):**

| Цена от OO | Смысл | Payout `[Yes,No]` | Redeem |
|---|---|---|---|
| `0` | **NO** (p1) | `[0,1]` | No=$1, Yes=$0 |
| `1e18` | **YES** (p2) | `[1,0]` | Yes=$1, No=$0 |
| `0.5e18` | **UNKNOWN / 50-50** (p3) | `[1,1]` | каждая доля = **$0.50** (штатная обработка спора/отмены/ничьи) |
| `int256.min` | **TOO_EARLY** (p4) | — | триггерит reset, не резолв |

**Курирование сеттлеров (важно для качества):** с UMIP-189 (авг. 2025) Polymarket мигрировал на Managed OO V2 — **предлагать исход могут только вайтлистнутые адреса** (критерий: ≥5 предложений за 6 мес. при точности ≥95%), но **диспуты остались пермишенлес для всех**. Эффект: точность предложений выросла до ~99.7%. Дополнительно есть аварийный `resolveManually()` (после `flag()` + 1 ч safety-period) и `pause()` как предохранитель. После финализации исход **необратим** — даже Polymarket не может переписать.

**UX-инсайт:** за минуты до резолюции выигрышные доли торгуются по $0.995–$0.999 — это «инстант-кэшаут» без ожидания оракула, фича ликвидности, а не баг.

### 1.5. Комиссии и liquidity rewards

**Комиссии.** Исторически 0/0 (главный маркетинговый аргумент годами). В 2025–2026 введены **динамические taker-комиссии** (maker = 0% всегда; sell не облагается). Формула:

```
fee = C × feeRate × p × (1 − p)
```
где `C` — число долей, `p` — цена (вероятность), `feeRate` — категориальная ставка. Свойство: множитель `p·(1−p)` максимален при `p = 0.50` и **симметрично падает к нулю у краёв** — комиссия бьёт по latency-арбитражу около 50% и почти не трогает «уверенные» рынки у краёв. Базовые `feeRate`: Crypto 0.07, Sports 0.03, Finance/Politics/Tech/Mentions 0.04, Economics/Culture/Weather/Other 0.05, **Geopolitics 0 (бесплатно)**. Эффективный пик из-за `p(1−p)≤0.25` вчетверо ниже базовой (Sports → 0.75%, Crypto → 1.80% при 50%).

> ⚠️ Конкретные проценты и даты ввода менялись в 2025–2026 и частично из вторичных источников — сверять на `docs.polymarket.com/trading/fees`. Сам принцип «maker 0% / taker платит, симметрия вокруг 50%» устойчив.

**Двойной стимул мейкеру** (поверх торговли):
- **Liquidity Rewards** — выплаты за resting-лимитки у мидпоинта. Квадратичный скоринг `S(v,s) = ((v−s)/v)² · b` (`v` = max spread, `s` = фактический спред от мидпоинта, `b` = размер): чем ближе к мидпоинту и крупнее — тем выше балл, штраф за удалённость квадратичный. Поминутные случайные снэпшоты (нельзя «мелькнуть» ордером), эпоха = сутки = 10 080 сэмплов. Бонус за **двустороннюю** глубину (`c = 3.0`); на экстремальных вероятностях `[0,0.10)` и `(0.90,1]` односторонняя ликвидность = 0 баллов (анти-фарм). Нормализация по рынку, выплата ежедневно в полночь UTC, минимум $1.
- **Maker Rebates** — 20–25% собранных taker-комиссий возвращается мейкерам, чьи ордера исполнили.

**Газ:** на Polygon субсидируется Polymarket через релейер/мета-транзакции — пользователю нужен только стейблкоин, депозит/вывод без комиссии платформы.

### 1.6. Мульти-исходные события (Negative Risk)

Для взаимоисключающих многоисходных событий («кто победит?») — набор бинарных рынков под одним event, помеченный `negRisk: true`, где **ровно один исход резолвится YES**. Свойство: **сумма всех YES-цен ≈ $1** (= 100%). Удерживается не вручную, а арбитражом через `NegRiskAdapter`:
- **Convert:** 1 NO-доля в одном рынке → по 1 YES-доле в каждом из остальных рынков набора (без доп. капитала). «Ставить против X = ставить за всех остальных».
- **Convert-арбитраж:** если сумма YES-цен < $1, скупаешь все YES дешевле $1, ровно один гасится за $1 → безрисковая прибыль (это и выравнивает сумму к $1).
- **Augmented neg risk** (`negRiskAugmented`): плейсхолдеры + «Other» + bulletin board позволяют добавлять кандидатов после старта, не пересоздавая рынок.

Резолюция: победивший YES → $1, все остальные YES → $0. UI-маппинг строки: `groupItemTitle` = подпись строки, `outcomePrices[0]` (цена YES) = процент, сортировка по убыванию вероятности.

### 1.7. Механика Polymarket → как переносим в Legio (на очках, LMSR)

| Механика Polymarket | Как устроено у PM | Перенос в Legio (очки + LMSR) |
|---|---|---|
| **Курируемое создание + децентрализ. резолюция** | markets team листит, UMA резолвит | Сохранить админское создание + обязательный 3-частный шаблон правил (источник + дата/таймзона + edge-cases); путь к репутации резолверов позже |
| **Event → Market → Outcome** | контейнер + бинарные рынки со slug | Завести таблицу `events`, `market_type` (binary/categorical), `event_id`; мульти-исход = N бинарных строк (P3) |
| **YES + NO = $1** через split/merge + арбитраж | гарантия CTF-контракта | **Бесплатно из LMSR-softmax:** `p_YES + p_NO = 1` математически, несуммирующееся состояние непредставимо. Split/merge/арбитраж **не нужны** |
| **Цена = вероятность** | $1/$0 выплата → цена = EV | Идентично: цена в ¢ = вероятность в %; **1 выигрышная доля = 1 поинт** |
| **CLOB** (off-chain матчинг + on-chain сеттлмент) | ордербук, EIP-712, оператор | **Не переносим в MVP.** LMSR — всегда-котирующий контрагент без стакана. CLOB — опциональный эндшпиль (P4); роль «ликвидности» играет параметр `b` |
| **mint/merge-матчинг (3 типа)** | удвоение глубины книги | Неприменимо — нет ордербука; глубина задаётся `b` |
| **Типы ордеров** (GTC/GTD/FOK/FAK), market в $/sell в долях, slippage-protection | лимитки + marketable | Перенести **UX-тикета**: BUY = трата в поинтах (chips), SELL = доли + «Продать всё», live-quote, «Выиграешь: X», `maxPriceCents` → `SLIPPAGE_EXCEEDED`. Лимиток нет (нет стакана) |
| **mid-price на карточке** | `(bid+ask)/2`, спред>10¢ → last | У LMSR спреда нет: показываем маржинальную softmax-цену напрямую; квоты bid==ask |
| **UMA-резолюция** (2 ч окно, бонды, DVM, p1–p4) | внешний ончейн-оракул | `PATCH …/resolve` (админ): выигравший исход → `доли×1` победителям, 0 проигравшим; спорный = payout-вектор `[0.5,0.5]`; необратимо + идемпотентно. **Лёгкий диспут**: окно ревью ~24ч + публичная запись резолюции (UMA-эффект без крипты) |
| **Кодировка p1/p2/p3/p4** | NO/YES/50-50/TOO_EARLY | `winning_outcome ∈ {YES,NO}` + `payout_vector` для спорных (50/50); отмена = возврат **себестоимости** |
| **Комиссии** `fee = C·feeRate·p·(1−p)` (maker 0, taker, симметрия) | динамические taker-fee | Поле `fee_bps` строим сразу, дефолт **0/0**. Дельта комиссии → реальная строка леджера `house:fees`, не сжигается. Симметричную `p(1−p)`-форму взять как готовую при включении комиссий |
| **Liquidity rewards** (квадратичный скоринг, двусторонность, снэпшоты) | стимул мейкерам | Неприменимо без ордербука/внешних LP; «ликвидность» обеспечивает `b`. Вернуться только вместе с CLOB (P4) |
| **Negative Risk** (сумма YES = $1, Convert) | арбитраж через адаптер | В LMSR мульти-исход **нативен**: N-исходный softmax даёт сумму=1 по построению; Convert-арбитраж невозможен. UI-нормировка для отображения 100% (P3) |
| **Gasless UX** (релейер, мета-тх) | субсидия газа на Polygon | Неактуально — играем на очках, ончейна нет; «баланс в поинтах» уже gasless по природе |
| **Леджер/сохранение средств** | ончейн-коллатерал заперт в CTF | Append-only `ledger` с инвариантом «сумма легов транзакции = 0»; `house:subsidy` префинансирует максимум `b·ln(2)`; проверяемое сохранение на каждой сделке/резолюции |

**Сквозной вывод:** значительная часть «магии» Polymarket (YES+NO=$1, цена=вероятность, сумма мульти-исходов=100%) у Polymarket обеспечивается ончейн-арбитражом поверх CTF, а в Legio те же инварианты даются **бесплатно из конструкции LMSR-softmax** — это и есть главный аргумент в пользу LMSR на старте. CLOB, mint/merge, liquidity rewards и gasless — это следствия ончейн-биржевой архитектуры; они переносятся только в опциональной фазе P4 и только если объёмы оправдают матчинг-движок. UX-слой (тикет «потратить X → выиграешь Y», карточка event→market, шаблон правил, диспут-окно с публичной записью резолюции) переносится полностью и сразу.

## 2. Графики и экраны Polymarket (эталон UX)

Этот раздел фиксирует целевой UX, на который равняется Legio. Структура: сначала эталонный график (ядро, переиспользуется на всех экранах), затем экран за экраном — деталь рынка, главная/дискавери, портфель/P&L, соц-функции, мобильный UX, онбординг. Везде, где деталь подтверждена первоисточником Polymarket — это «копировать один-в-один»; помечено `[набл.]` то, что выведено по наблюдению за фронтом, а не из доков.

### 2.1. График вероятности — анатомия и поведение

Главный график на странице рынка — это **вероятность во времени**, а не свечи и не цена в абстрактных единицах. Ось Y = 0–100% (цена доли $0.00–$1.00, отрисованная как проценты). Это прямое следствие нашего LMSR-инварианта `p_YES + p_NO = 1`: график линии — это `p_i` из softmax во времени.

**Ключевые свойства линии:**

| Свойство | Поведение (эталон) | Привязка к Legio |
|---|---|---|
| Ось Y | 0–100%, линейная; «65% chance» = цена доли $0.65 | `p_i × 100`, где `p_i` — softmax-цена |
| Тип | Линия (area/line), не свечи; плавная между точками | соединяем точки ряда |
| Источник текущей точки | midpoint бид/аск; **при спреде > $0.10 — last trade** | у нас нет ордербука → берём `last_yes_price` (авторитетная колонка), это снимает D5 |
| Бинарный рынок | одна линия YES, NO — зеркало; крупная цифра «N% chance» над графиком | рисуем только YES |
| Categorical | мультилиния: по линии на исход, общая ось времени и 0–100% | по линии на исход через его `p_i` |

**Диапазоны (таблетки-переключатели) — копировать набор и маппинг один-в-один:**

| Кнопка UI | Polymarket `interval` | Гранулярность (`fidelity`) | Применение в Legio |
|---|---|---|---|
| 1H | `1h` | поминутно (1 мин) | мелкая агрегация |
| 6H | `6h` | минуты | |
| 1D | `1d` | минуты/часы | дефолтный вид |
| 1W | `1w` | часы | |
| 1M | `1m` | часы/сутки | |
| ALL | `max` (`all`) | крупная (адаптивная) | весь срок жизни рынка |

Поведение: клик по таблетке → перезапрос ряда с соответствующим `interval` и адаптивным `fidelity` → перерисовка. Один активный диапазон подсвечен. **Адаптивный `fidelity` обязателен:** для 1H — поминутно, для ALL — крупно, иначе тянем миллионы точек. Ловушка Polymarket, которую закладываем сразу: на **закрытых/разрешённых рынках** исторический ряд деградирует до гранулярности 12+ часов — для завершённых событий 1H не предлагаем (кнопка скрыта/недоступна).

Формат точки ряда (наш аналог Polymarket `prices-history`): `{ t: unixSeconds, p: 0..1 }`. Линия — просто эти точки; Y масштабируется ×100. Эндпоинт Legio должен принимать `interval` и `fidelity` и отдавать ровно такой ряд, чтобы фронт-компонент графика был дословной копией поведения Polymarket.

**Hover / crosshair / тултип:**
- При наведении — вертикальный курсор-кроссхэйр, привязанный к ближайшей точке времени.
- Тултип показывает **дату/время + значение(я) в процентах**.
- Для мультилинии тултип выводит значения **всех исходов одновременно** на этой временной отметке. `[набл.]`
- Над графиком для бинарного рынка — крупная текущая цифра «N% chance» + дельта направления (см. ниже).

**Цвет направления (зелёный/красный) — для бинарных и дельт:**
- Зелёный = рост вероятности за выбранный период, красный = падение. Подпись «▲ +5%» / «▼ −3%».
- Привязка дельты к выбранному таймфрейму (дельта 1D при диапазоне 1D и т.д.). `[набл.]` точная привязка периода у Polymarket не задокументирована; берём «дельта = изменение за активный диапазон».
- У нас источник дельты — разница `p_i` между первой и последней точкой ряда выбранного диапазона (аналог Polymarket-полей `oneHourPriceChange` / `oneDayPriceChange` / `oneWeekPriceChange` / `oneMonthPriceChange`). Стоит завести эти производные поля на рынке, чтобы карточки красились без запроса полного ряда.

**Мультилинии для categorical (мульти-исход):**
- Categorical-событие = бандл связанных исходов; график накладывает по линии на исход, линия = `p_i` этого исхода.
- Цвета линий — **стабильная палитра по исходам** (каждому исходу свой фиксированный цвет), НЕ зелёный/красный. Зелёный/красный зарезервированы под направление в бинаре/дельтах.
- **Легенда:** список исходов с цветными маркерами и текущим %, отсортированный по убыванию вероятности; клик по элементу скрывает/показывает линию. `[набл.]`

**Объём (volume):**
- Объём выводится **отдельной метрикой-числом** («$1.2M Vol» / у нас «1.2M pts Vol»), а НЕ столбиками под линией вероятности. Основной график остаётся чистой линией вероятности — это сознательное решение Polymarket, копируем.
- Рядом отдельно показываем **ликвидность** (у нас это параметр `b` LMSR, поданный как «глубина рынка»).

**Спарклайны в карточках:**
- Мини-линия без осей, легенды и подписей; инлайн-элемент в карточке.
- Строится тем же рядом, что и большой график, но коротким диапазоном (обычно `1d`).
- Цвет спарклайна красится **по знаку дельты** соответствующего периода (зелёный рост / красный падение). `[набл.]` точную кодировку Polymarket не документирует — красим по знаку change, это разумная и проверяемая реализация.

### 2.2. Экран детали рынка (market detail)

Эталонная раскладка desktop — двухколоночная: широкая левая колонка (контент) + узкая правая sticky-колонка (тикет). Четыре смысловых блока: **Market Overview → Order Book → Rules → Community**. Для Legio (LMSR, без ордербука) блок Order Book заменяется на «Глубину/depth по кривой LMSR» либо опускается в P1.

**Шапка (в один взгляд):**
- Иконка рынка + текст вопроса.
- **Текущий %** = цена исхода (цена = вероятность: $0.25 = 25%). Берётся midpoint, при спреде >$0.10 → last trade; у нас — `last_yes_price`.
- Дельта направления (зелёный/красный), синхронная таймфрейму графика.
- **Volume** (суммарный объём), **Liquidity** (у нас — `b`/глубина), **дата закрытия**.
- Live-индикатор для спортивных/live-событий (real-time odds + счёт). `[набл.]` визуал бейджа известен по проду.

**Тикет покупки/продажи (sticky справа) — самый копируемый элемент.** Это напрямую закрывает наш диагноз D7 (нет превью выплаты/P&L):

| Элемент тикета | Эталон Polymarket | Реализация в Legio (LMSR/очки) |
|---|---|---|
| Тоггл Buy / Sell | вверху | да |
| Тип ордера Market / Limit | переключатель | в P1 только Market (LMSR-котировка); Limit — позже |
| Кнопки исхода с ценой НА кнопке | `Yes 64¢` / `No 36¢` | да; цена = `p_i` |
| Поле ввода (Market) | сумма в $, быстрые **+$1 / +$5 / +$10 / +$100**, мин. $1 | сумма в **поинтах**, пресеты +1/+5/+10/+100 pts, режим «трата S» из мастер-плана §2.2 |
| Поле ввода (Limit) | shares, кнопки −100/−10/+10/+100 + Limit Price, мин. 5 shares | позже |
| **Avg price** | средняя цена исполнения | `cost / Δ` из LMSR |
| **Total** | стоимость ордера | `cost` |
| **To win** | выплата если исход сыграет (1 доля = $1) | `shares × 1 pt` — критичный мотивирующий лейбл |
| Комиссии | maker 0% / taker dynamic fee, пик на 50% | поле `fee_bps` уже в движке; на старте 0/0 |
| Кнопка действия | Buy / Sell | да |

Обязательно скопировать: **цену исхода прямо на кнопке**, **быстрые кнопки докидывания суммы**, явный **«To win»**, разделение единиц (у нас: сумма BUY в поинтах, кол-во SELL в долях — и НЕ переиспользовать один и тот же стейт между ними, это была ошибка D7). Заголовок тикета — «Покупка/Ставка», НЕ «Голосование» (диагноз D8).

**Вкладки под графиком:**
- **Order Book / Depth:** у Polymarket — bids/asks по уровням + spread. У нас ордербука нет — показываем **кривую глубины LMSR** (сколько стоит сдвинуть цену на X), либо опускаем блок в P1.
- **Top Holders:** крупнейшие позиции **раздельно по сторонам** (Yes-holders / No-holders через `outcomeIndex`), до 20 на сторону; по каждому — аватар, имя, размер позиции; клик → профиль с P&L (фундамент copy-trading).
- **Activity:** лента последних сделок по рынку (кто, исход, размер, цена, время), real-time.
- **Comments:** аватар, текст, реакции/лайки, вложенные ответы (`parentCommentID`), бейджи. Две сильные фишки к копированию: фильтр **`holders_only`** (только комментарии тех, у кого есть позиция) и **показ позиции рядом с автором** («на что он поставил, когда это пишет»).

**Rules / Resolution (Rules-first):** жёстко выделенный блок из трёх обязательных элементов — **источник резолюции**, **end date**, **edge cases**. Видимый статус процесса резолюции. У Polymarket это UMA-машина (Open → Proposed → Disputed → Resolved, bond ~$750, окно споров 2 ч); у Legio резолюция админская (мастер-план §2.2: `winning_outcome` + расчёт выплат), но **статус-бейдж и блок правил подаём так же явно** — пользователь должен понимать, по каким правилам платят, ещё до сделки.

### 2.3. Главная / дискавери

Стратегический сдвиг Polymarket (конец 2025): главная — это **новостной терминал**, а не «биржа пар». Месседж: «значимое изменение вероятности = breaking news». Это меняет цель воронки — не «выбрать пару для сделки», а «понять, что происходит». Для Legio это ориентир позиционирования главной.

**Анатомия главной (сверху вниз):**
1. **Hero-карусель** из ~7 high-profile событий: на карточках живой линейный график вероятности (не статичный спарклайн), объём за сегодня, стрелки роста/падения, реал-тайм активность.
2. **Breaking News (правый сайдбар):** лента значимых движений с зелёным индикатором роста %; формат «вывод одним числом + его изменение».
3. **Hot Topics:** модуль тем-ключевых-слов, ранжированный **по реальному объёму торгов** («тренд по деньгам, а не по кликам»).
4. **Основная сетка «All markets»** (второй экран) с сортировками и переключателями **Hide sports / Hide crypto / Hide earnings** (управление шумом доминирующих категорий).

**Сортировки (копировать набор, включая редкий `Competitive`):** `New`, `Trending`, `Popular` (по объёму), `Liquid` (по ликвидности), `Ending Soon`, `Competitive` (около 50/50). **Статус-фильтры:** `Active / Resolved / All`. **Переключатель формата цены** (% / центы / American / Decimal) — расширяет аудиторию беттинга; для Legio минимум `% / центы`.

**Анатомия карточки рынка (копировать построчно):**
- Вопрос/тайтл + категория-теги.
- **Крупный %** вероятности.
- **Кнопки исхода Buy Yes / Buy No с ценой.** Важный нюанс ценообразования: отображаемый % = midpoint (при спреде >$0.10 — last trade), НО при клике платишь lowest ask — отображаемая и исполняемая цена сознательно расходятся. У нас (LMSR) аналог: показываем `p_i`, а реальная средняя цена исполнения `cost/Δ` выше из-за проскальзывания по кривой издержек — нужно это явно показать в тикете.
- **Спарклайн** (на hero-карточках — живой график).
- **Volume** и отдельно **Liquidity** (Polymarket показывает оба — depth информативнее цены).
- **Таймер / дата события**, **счётчик комментариев**, **иконка-закладка (bookmark / watchlist)**, **источник-атрибуция** (ссылка на новостной аутлет — часть «news terminal»).
- Мульти-исход: каждый исход — **отдельная строка** со своим `% chance` и своими кнопками.

**Slug-архитектура:** события/рынки/категории имеют человекочитаемые slug в URL (`/predictions/<slug>`, `/<topic>`), которые служат одновременно навигацией, deep-link и API-ключом. Закладываем это сразу.

### 2.4. Портфель / P&L

URL-эталон `polymarket.com/portfolio`. Это закрывает наш критичный UX-диагноз D7 (портфеля нет вообще).

**Хедер портфеля — 3 числа + график:**
- **Portfolio value** — суммарная mark-to-market стоимость позиций + кэш.
- **Cash / Available** — баланс, не вложенный в позиции (у нас — `points_balance`).
- **Profit/Loss** — итоговый P&L с переключателем периода **1D / 1W / 1M / All** и графиком доходности.

**Вкладки:** Positions (дефолт) · Open Orders · History/Activity.

**Таблица открытых позиций — точные колонки (копировать):**

| Колонка | Смысл | Поле в Legio |
|---|---|---|
| Market / Outcome | рынок + исход + иконка | есть |
| Shares (Quantity) | число долей | `shares_micro` |
| Avg → Price | средняя цена входа → текущая цена | `avgPriceCents` → `p_i` |
| Bet / Amount | вложено (cost basis) | `initialValue` |
| Value | текущая стоимость = shares × current price | `shares × p_i` |
| **To win** | макс. выплата = shares × 1 | `shares × 1 pt` |
| **P/L** | нереализованный P&L: в единицах И в %, цветом | нужно завести `cashPnl` + `percentPnl` |

**Ключевой вывод (модель данных):** реализованный и нереализованный P&L хранятся как **отдельные поля на уровне позиции** (`cashPnl`/`percentPnl` — нереализованный, `realizedPnl`/`percentRealizedPnl` — реализованный). Нативный Polymarket за слабое разделение этих двух на экране как раз критикуют — Legio должна **чётко разделить realized/unrealized в UI с самого начала**.

**История (Activity):** лента операций с типами `TRADE / SPLIT / MERGE / REDEEM / REWARD / CONVERSION`; поля события — `timestamp, type, side, size, usdcSize, price, outcome, title, transactionHash`. Для Legio достаточно `TRADE` и `REDEEM` (расчёт по резолюции) в P1.

**Claim / Redeem:** у решённой позиции кнопка **Trade → Redeem/Claim**; выигрышная доля = 1 поинт, проигрышная = 0. Опционально **Auto-Redeem** (однократный approval, далее автоматом). У нас расчёт делает резолюция (мастер-план §2.2), но кнопка/состояние «забрать выигрыш» должны присутствовать в UI портфеля.

**Где обогнать Polymarket (известные пробелы):** нативный портфель НЕ даёт графиков доходности по отдельным позициям, слабо разделяет realized/unrealized на экране, хранит ограниченную историю, не показывает win-rate, нет CSV-экспорта (на global). Legio закладывает сразу: разделение realized/unrealized, полный аудируемый ledger (по образцу Polymarket US Position Ledger: `quantityChange`, `costChange`, `realizedChange`, `netPosition`, кумулятивный `realized`), графики P&L по периодам и по позициям, win-rate.

### 2.5. Соц-функции (лидерборд / активность / комментарии / Top Holders)

Все соц-данные у Polymarket — из публичных API; идентификатор пользователя везде — адрес (proxyWallet), username/pseudonym — слой поверх. Для Legio идентификатор — userId, имя — отображаемый слой.

**Лидерборд.** URL-паттерн с состоянием в URL (шарится): `/leaderboard/{category}/{period}/{metric}`.
- Окна: **DAY / WEEK / MONTH / ALL** (UI: Today / Weekly / Monthly / All).
- Сортировка: **PNL / VOL** (табы Profit/Loss и Volume).
- Категории: Overall, Politics, Sports, Crypto, Culture, Tech, Finance и т.д.
- Колонки строки: ранг, аватар + кликабельный username → профиль, P&L в $, объём, иконка X, бейдж верификации. Пагинация ~20–25/стр.
- Виральный блок **«Biggest wins this {period}»** — лента крупнейших единичных выигрышей (имя + рынок + сумма). Копировать обязательно.

**Публичный профиль.** URL `/@{username}`. Шапка: имя, аватар, дата регистрации, просмотры, соц-ссылки. **4 карточки метрик:** Positions Value · Profit/Loss · **Biggest Win** · Predictions (число рынков). **График P&L** с селекторами 1D / 1W / 1M / 1Y / YTD / ALL. **Табы:** Positions (под-фильтр Active/Closed) · Activity. Флаг приватности `displayUsernamePublic`.

**Активность (Activity).** Лента действий: кто купил/продал какой исход, сколько долей, по какой цене, на какую сумму, время + ссылка на транзакцию. Используется и в табе под рынком. **Real-time через WebSocket**, не поллинг.

**Комментарии (Discussion).** Под-табы: Comments (с фильтром Holders) / Top Holders / Activity / Related markets. Поля: `body`, `createdAt`, `parentCommentID` (треды), `reactionCount`, `reportCount`. Live через события `comment_created / comment_removed / reaction_created / reaction_removed`. Главная фишка к копированию — фильтр **«Holders»** (комментарии только от тех, у кого есть позиция = «скин в игре») + видимая позиция рядом с автором.

**Top Holders.** Две колонки — держатели Yes и держатели No (через `outcomeIndex`), отсортированы по размеру позиции; аватар, имя, размер; клик → профиль (P&L, история). Сильный сигнал прозрачности и база copy-trading. Связанный показатель — суммарная стоимость позиций пользователя (карточка Positions Value).

**Пуши/уведомления — пробел Polymarket, который Legio стоит закрыть:** натив покрывает в основном крупные движения цены и резолв рынка; «ордер исполнен», «ответили на коммент», «кит вошёл в твой рынок» — слабо. Закладываем эти триггеры сразу.

### 2.6. Мобильный UX

Для Polymarket мобайл — не второй экран, а **главный (часто единственный) канал** (десктоп-домен в США геоблокируется). Принцип всего мобильного UI: «сначала потребитель информации/новостей, потом трейдер» — тяжёлые трейдерские элементы (order book, гистограммы объёма) намеренно спрятаны глубже.

**Лента/домашний экран:** плиточная сетка карточек, ощущается как новостная лента; сверху горизонтальная карусель трендовых карточек; под ней горизонтальный скролл-бар категорий (тап = смена категории без ухода с экрана); фильтры/меню — крупные тач-таргеты.

**Карточка (узкий экран):** доминирует крупный **%**, рядом **цена в центах** (двойной формат «67% / 67¢» — вероятность для новичков, центы для трейдеров), цветовая кодировка исходов, миниатюра-картинка, объём, и часто **кнопки Yes/No прямо в карточке** (tap-to-buy из ленты). Мульти-исход — топ-кандидаты строками с их %.

**График на узком экране (критичная жестовая деталь):**
- Чистая линия с цветовой кодировкой исходов, не свечи.
- Таймфреймы табами 1H / 6H / 1D / 1W / 1M / ALL. `[набл.]` точный набор лейблов текущего релиза скриншотом не подтверждён.
- **Правило разделения жестов: горизонтальный свайп = скраб/пан графика, вертикальный = скролл страницы.** Это критично для качества мобильного чарта — копировать обязательно. На картах — pinch-to-zoom без конфликта со скроллом.

**Тикет на мобиле** (закреплён снизу / bottom-sheet): тумблеры Market/Limit и Buy/Sell, выбор исхода с ценой, ввод суммы через пресеты **+$1/+$5/+$10/+$100**, мгновенный **«To win»**, мин. $1 (market) / 5 shares (limit). На рыночном ордере поле цены = **worst-price лимит (защита от проскальзывания)**, а не целевая цена. Покупка «в один-два тапа».

**Прочее:** портфель сгруппирован **по категориям** (P&L по доменам); отдельная live-спорт витрина со счётом; **AI-сводка новостей на детали рынка** (у Polymarket — Perplexity) как драйвер удержания. Эксперимент-кандидат: swipe-режим а-ля Polyswipe (вправо = Yes, влево = No). Слабое место Polymarket = почти нет «engagement layer между сделками» — окно для дифференциации Legio (watchlist, алерты, swipe).

### 2.7. Онбординг / обучение

Цель — снизить порог входа. Главный обучающий месседж, который надо встроить в продукт буквально: **«Цена = Вероятность»**.

**Принципы подачи обучения (копировать):**
- Каждая доля стоит между $0.00 и $1.00; цена = вера рынка в вероятность исхода. Yes по $0.65 ≈ 65%.
- Бинарный рынок: Yes + No = $1.00 (у нас — ровно наш LMSR-инвариант `p_YES + p_NO = 1`, т.е. обучение и движок говорят одно и то же).
- Выплата: выигравшая доля = $1 (1 поинт), проигравшая = $0. Пример с числами: купил Yes по $0.18 → если исход наступит, доля = $1 → прибыль $0.82/доля.
- Цена объясняется как midpoint спреда, маркет-мейкеры названы «просто трейдеры, ставящие лимитные ордера» — снимаем жаргон.
- Страница рынка читается **меньше чем за 10 секунд** — это явный целевой KPI читаемости.

**Структура обучения по нарастанию сложности:** нарратив (что такое prediction market) → визуальные схемы → **таблицы действий** («когда покупать Yes / покупать No / продавать») → потом резолюция.

**Снижение порога через практику:**
- **Demo/Training-режим с виртуальным балансом** (у Polymarket упоминается ~$1000) для безрисковой тренировки. Для Legio это особенно органично — мы уже играем на очках, так что «тренировка = тот же движок».
- Гайд «первый трейд» учит процессу, а не профиту: «читай цену как вероятность, ставь мало, сверь источник резолюции». Рекомендованная первая сделка — маленькая.

**Онбординг-вход (если/когда появятся реальные деньги — задел на будущее):** passwordless по умолчанию (email magic-link / Google), «невидимый Web3» (embedded-кошелёк + смарт-контракт-прокси), газлесс-UX через релеер, мульти-чейн бридж с авто-свопом и низким минимумом, фиат on-ramp + Apple/Google Pay. Для play-money-версии Legio это пока не нужно, но архитектуру онбординга строим так, чтобы реальные деньги встали поверх без переписывания (соответствует решению заказчика из мастер-плана).

## 3. Текущее состояние Legio: что реально работает и где дыры

Главный сдвиг с момента диагноза из раздела 1: критические D1–D3 **уже закрыты в движке и бэкенде**. Победителям реально платят, деньги сохраняются через двойную запись, а `YES + NO = 100` держится математически (softmax). Оставшиеся дыры сместились с «ядра экономики» на **(а) UI-каналы, которые не подключены к готовому бэкенду**, **(б) синтетическую историю цен**, **(в) отсутствие портфеля/лидерборда/событий** и **(г) мульти-исход на Postgres**. Ниже — честная сводка по слоям с точными ссылками `file:line`.

### 3.1 Торговый движок / LMSR — **работает**

LMSR переписан как чистые функции (`server/lib/lmsr.js`) и реально подключён в исполнение, а не только в план. Старой формулы `impact`/`counterImpact` в коде нет вообще (grep пуст) — D3/D4 мертвы.

- Цепочка исполнения: `applyTrade` (`server/index.js:2186`) → `calculateFill` (`:574`) → BUY `lmsr.sharesForSpend` (`:590`), SELL `lmsr.proceedsForSell` (`:597`), новое состояние `lmsr.applyShares` (`:604`), цена `lmsr.priceYes` (`:605`).
- Математика устойчива: `priceYes` через log-sum-exp (`lmsr.js:41`), `sharesForSpend` в закрытой форме (`:76`), bounded loss `maxSubsidy = b·ln2` (`:98`), `bFromLiquidity = liquidity/ln2` (`:22`).
- `YES + NO == 100` гарантировано конструкцией: `noPrice = 100 - yesPrice` (`getDisplayPrices` `:551`). Тесты `lmsr.test.mjs` проходят: `node server/lib/lmsr.test.mjs` → **446896 assertions passed, 0 failed** (инвариант суммы на 100k состояний, монотонность, инверсия spend↔shares, lossless round-trip, bounded house loss).
- `/quote` реализован: `POST /api/markets/:id/quote` (`:2740`) → `quoteTrade` (`:1955`), превью без списания, возвращает shares/cost/fee/avgPrice/toWin/returnPercent.
- Защита от двойного списания (Postgres): атомарная транзакция + пессимистичные `SELECT ... FOR UPDATE` на рынок, юзера, позицию (`:1844–1848`); те же блокировки в `resolveMarket` и `cancelMarket`.

**Дыры движка:** (1) **мульти-исход на Postgres не работает** — `placeTrade` бросает `MULTI_PG_UNSUPPORTED` (`:1857`); мульти живёт только на JSON-хранилище (`:1919`) → в проде с PG категориальные рынки неторгуемы. (2) **Нет CLOB/ордербука/лимит-ордеров** — только AMM-исполнение по рынку, `bid==ask` (`:765`), нет maker/taker. (3) **JSON-ветка без блокировок** (`:1896`) — конкурентные записи теряют апдейты (фолбэк-режим, небезопасен в проде).

### 3.2 Резолюция / леджер / выплаты — **работает, но без глобального инварианта**

Победителям реально платят — это не смена статуса. D1/D2 закрыты.

- `resolveMarket` (`server/index.js:1989`): каждая позиция с `outcome === winningOutcome` получает `payout = shares` (1 поинт/доля, `:2005`), баланс растёт (`:2007`), позиция обнуляется (`:2010`); всё в транзакции с `FOR UPDATE` и защитой `MARKET_ALREADY_SETTLED` (`:2001`).
- `cancelMarket` (`:2057`): возврат остаточного `cost_basis` каждому холдеру (`:2073–2075`) — корректно для AMM.
- Леджер: таблица `ledger` (`:1011–1021`), двойная запись `balancedLegs` (`:2134`), запись `recordLedgerPg/Json` (`:2154/2166`), per-transaction инвариант `assertBalanced` → `LEDGER_IMBALANCE` (`:2143`). Денежные роуты отделены от статусных: `/status` пускает только `open`/`paused` (`:2639`), деньги — только через `/resolve` (`:2651`) и `/cancel` (`:2670`).

**Дыры:** (1) **Нет глобального инварианта сохранения** — `assertBalanced` проверяет только нулевую сумму внутри одной транзакции; reconciliation-функции/эндпоинта (`SUM(delta) GROUP BY account`) нет. (2) **Леджер write-only** — ни одного `SELECT FROM ledger`, нет аудита/восстановления балансов. (3) **Аккаунт `house` не сидируется** — нет материализованной строки, сверить нельзя. (4) **Нет валидации выигравшего исхода** — `resolveMarket` принимает любую строку; опечатка → рынок «зарезолвится», никто не получит выплату, средства осядут в house. (5) Нет частичной/invalid-резолюции (50/50), нет dispute/оракула/таймлока — резолюция мгновенная и необратимая по решению одного админа.

### 3.3 История цен (бэкенд) — **синтетическая, не хранится**

История **фабрикуется на лету из seed**, реальной серии нет. Таблицы `price_history` нет.

- `priceHistory.js:5–21` прямо документирует: «Pure functions only: no I/O… seeded ONLY by the marketId». Путь = равномерная по времени сетка (`buildEvenTimeGrid` `:63`) + piecewise-linear baseline + fBm-шум (`:116–174`).
- Реальные сделки используются лишь как «вехи», раскладываемые **по индексу, а не по timestamp** (`buildSpreadAnchors` `:86–92`, комментарий `server/index.js:809–811`) → временная ось не соответствует реальному времени сделок.
- Формат точек — преформат: бинарный `{ time: ISO, yesPercent, noPercent }` (`server/index.js:823`), мульти `{ time, values:{...} }` (`:858`). Поля `{t,p,v}` и объёма по точке нет.
- Окно фиксировано `[createdAt, now]` (`:782–788`); **range/interval не читаются нигде** (грепы дают только rate-limiter buckets). Кап 140 точек (`priceHistory.js:25`). Вход — только последние 80 сделок (`getTrades(id,'desc',80)` `:1763`) → ранняя история старых рынков теряется.

**Дыры:** нет персистентной серии → невозможны корректные «изменение за 24ч»; нет range-переключателя, бакетирования, forward-fill, OHLC, объёма по точке.

## 4. Большой план переработки интерфейса Legio (экран за экраном)

Этот раздел — исполняемая спецификация переработки UI. Сквозной принцип: **экономика читается на каждом экране**. Везде, где есть цена, она = вероятность; везде, где есть позиция, видно «сколько вложил / сколько стоит сейчас / сколько выиграю / P&L»; везде, где есть резолюция, есть явное действие забрать выигрыш и видимая сумма.

### 4.0 Единая модель единиц (закон, обязательный для всех экранов)

Это фундамент. Сейчас в коде смешаны `$`, `pts`, `¢` без якоря (см. `[C8]`: объёмы в USD, баланс в pts, цена в ¢, плейсхолдеры в `$100 000`). Вводим единый словарь и единственный форматтер.

| Сущность | Единица | Формат | Где живёт |
|---|---|---|---|
| Баланс / стоимость / объём / выплата | **поинт (pt)** | `1 234 pt`, дробные до 2 знаков `12.50 pt` | `formatPoints()` в `utils.ts` |
| Цена доли / вероятность | **¢ = %** (тождество) | `64¢` ↔ `64%` (одно число, переключатель формы) | `formatPrice()` |
| Размер позиции | **доля (share)**, 1 выигрышная доля = **1 pt** | `12.5 долей` | `formatShares()` |
| Изменение цены | **процентные пункты (п.п.)** | `▲ +5%` / `▼ −3%` | `formatDelta()` |

### 4.3 Тикет покупки/продажи (центральный экран экономики)

Это сердце продукта. Сейчас (`[C4]`): live-quote, слиппедж-гард, P&L-бейдж — **реализованы и корректны**; но есть реальные баги единиц в SELL, нет redeem-кнопки на resolved, остался CTA «голосовать» для гостя.

**Единая модель единиц тикета (закрепляем):**
- Цена доли в **¢ = %** (62¢ = 62%).
- 1 выигрышная доля = **1 pt** → «Выиграешь X pt» = число долей.
- **BUY:** ввод = **сумма в pt к трате** (режим «трата») ИЛИ **число долей** (режим «доли»).
- **SELL:** ввод = **число долей** к продаже (можно дробные); «Получишь» = pt.

**Раскладка тикета (текстовый макет):**
```
┌───────────────────────────────┐
│ Сделка   Цена = вероятность ·  │
│          выигрыш 1 pt за долю  │
│ [ Купить | Продать ]           │ ← сегмент-контрол
│ [ YES 62¢ ] [ NO 38¢ ]         │ ← кнопка с ценой; зелёный/красный
│                                │
│ Режим: ( Трата pt | Доли )     │ ← только для BUY
│ ┌────────────────────────────┐ │
│ │  Сумма:  [   100   ] pt    │ │ ← BUY-трата: pt; BUY-доли/SELL: доли
│ └────────────────────────────┘ │
│ [+10][+50][+100][+500]  или    │ ← чипы; для SELL: [25%][50%][Max]
│ [25%][50%][Max] (SELL)         │
│                                │
│ ── ЖИВОЙ QUOTE-ЧЕК ──          │
│ Доли:          161.2           │
│ Средняя цена:  62.0¢           │
│ Проскальзывание: +0.4¢         │
│ Выиграешь:     161.2 pt  +61%  │ ← toWin + returnPercent (BUY)
│ (SELL) Получишь: 99.4 pt        │
│ Комиссия:      0 pt            │
│ У тебя долей:  12.5 (баланс)   │ ← НЕ «Получишь»! (фикс бага)
│                                │
│ ── ТВОЯ ПОЗИЦИЯ (если есть) ── │
│ Вложено 80 pt · Сейчас 100 pt  │
│ P&L: ▲ +20 pt (+25%)           │ ← зелёный/красный
│                                │
│ [   Купить YES — 100 pt   ]    │ ← цветная кнопка
│ Проскальзывание защищено ±5¢   │
└───────────────────────────────┘
```

**Живой quote-чек — обязательные строки:**

| Строка | BUY | SELL | Источник |
|---|---|---|---|
| Доли (shares) | да | да (продаваемые) | `quote.shares` |
| Средняя цена | да | да | `quote.avgPriceCents` |
| Проскальзывание | `priceImpactCents` | да | `quote.priceImpactCents` |
| Выиграешь / Получишь | «Выиграешь X pt + Y%» | «Получишь X pt» | `quote.toWin` / `quote.cost` |
| Комиссия | если >0 | если >0 | `quote.fee` |
| Баланс/позиция | «Баланс: N pt» | «У тебя долей: N» | `viewer` |

**Колонки таблицы позиций (по модели Polymarket):**

| Колонка | Смысл | Источник |
|---|---|---|

**Раздельный realized/unrealized (преимущество над Polymarket):** хранить и показывать `unrealizedPnl` (открытые, mark-to-market по текущей `p`) и `realizedPnl` (закрытые/проданные) **отдельно** — нативный Polymarket за слабое разделение критикуют. ### 4.8 Онбординг / How It Works (`/how-it-works`)

Объясняет экономику новичку. Текущий экран есть; переработать под единую модель единиц.

**Содержание (секции):**
```

5. Резолюция
   Рынок закрывается → админ публикует исход по правилам →

6. P&L и Портфель
   Вложено / Стоимость сейчас / Выиграешь / P&L.
[ Открыть первый рынок ]   [ Перейти в Портфель ]
```

## 5. Дизайн-система, информационная архитектура и единая модель экономики в UI

Этот раздел задаёт **единый визуальный и смысловой язык** Legio: одну валюту, одно правило «цена = вероятность», один набор переиспользуемых компонентов и одну, отвязанную от языка, таксономию. Цель — чтобы карточка, деталь, тикет, портфель и админка говорили об одних и тех же трёх числах **одинаково**, а не как три разных продукта (см. диагноз D7/D8 в мастер-плане). Раздел готов к исполнению: каждая подсекция даёт конкретные правила, токены и список компонентов с пропсами.

### 5.1 Единая ментальная модель и единицы

Сейчас в продукте сосуществуют три несогласованные единицы (¢ за долю, `pts` за баланс, `$` в маркетинговых строках) и две ментальные модели — «голосование/поддержка поста» и «трейдинг долями» (источник `C8`). Чиним это **жёстким набором аксиом**, обязательным для всего UI и копирайта.

**Аксиомы (единый якорь, повторяется на каждой высоте):**

| # | Правило | Следствие для UI |
|---|---------|------------------|
| A1 | **Одна валюта — поинты (points / pts).** Никаких `$`, `USD`, `currency:'USD'` в `formatMoney`. | Баланс, объём, стоимость позиции, P&L — всё в поинтах. Один форматтер `formatPoints()`. |
| A2 | **Цена доли = вероятность.** `¢ == %` — одно и то же число. Доля стоит 0–100¢, что читается как 0–100%. | Ценовой бейдж показывает либо `64¢`, либо `64%` (переключатель формата), но это одно число. |
| A3 | **1 выигрышная доля = 1 поинт.** Проигрышная = 0. | «Выиграешь» = `доли × 1 поинт`. Везде один лейбл-якорь. |
| A4 | **YES + NO = 100¢ = 100%** всегда (гарантия LMSR-движка). | NO-цена никогда не показывается отдельным запросом: `noPrice = 100 − yesPrice` на клиенте. |
| A5 | **Никакого «голосования».** Только Купить/Продать/Сделка/Ставка. | Удалить `voteTitle`, `loginToVote`, `api.vote()`, `common.supported`, «посты-рынки». |

**Правило отображения цены (копируем у Polymarket, источники `R2`/`R7`):**
- Базовое отображение `%` = **midpoint** котировки. В LMSR-модели Legio это напрямую `p_YES` из softmax — спреда нет, поэтому midpoint = мгновенная цена.
- Когда появится CLOB (P4) — добавить правило «если спред > 10¢, показывать last-trade price». До тех пор это поле не нужно, но компонент `PriceBadge` должен принимать `displayMode`, чтобы переход был безболезненным.

**Конвертация и форматирование (единый слой, в `utils.ts`):**

| Величина | Внутреннее представление | Формат в UI (RU/EN) |
|----------|--------------------------|---------------------|
| Деньги | `micro` (1 поинт = 1 000 000 микро) | `formatPoints(micro)` → `1 250 pts` / `1,250 pts` |
| Цена/вероятность | `cents` (0–100) | `formatPriceCents(c, mode)` → `64¢` или `64%` |
| Доли | `micro`-доли | `formatShares(micro)` → `12,5 доли` / `12.5 shares` |
| P&L | `micro`, знаковое | `formatPnl(micro)` → `+340 pts` (зелёный) / `−120 pts` (красный) |
| Доходность | дробь | `formatReturn(x)` → `+38%` |

Правило: **компоненты не форматируют сами** — только через эти функции. Это убивает «размазанное по компонентам» форматирование (диагноз `C8`).

**Якорь-строка тикета (одна на весь продукт):** «Цена = вероятность. Выигрышная доля = 1 поинт.» (`market.orderMode` — уже есть, оставить и не дублировать другими формулировками).

### 5.2 Токены дизайна

Все токены — CSS-переменные в одном файле (`:root` + `[data-theme="dark"]`), компоненты ссылаются только на переменные. Семантика направления (зелёный/красный) — **строго по смыслу «вверх/вниз / выигрыш/проигрыш»**, не по бренду.

**Цвет — направление и исход:**

| Токен | Светлая | Тёмная | Назначение |
|-------|---------|--------|------------|
| `--dir-up` / `--yes` | `#16a34a` | `#22c55e` | Рост вероятности, YES, прибыль, «Купить Да» |
| `--dir-down` / `--no` | `#dc2626` | `#ef4444` | Падение, NO, убыток, «Купить Нет» |
| `--dir-flat` | `#6b7280` | `#9ca3af` | Без изменения, нейтраль, проигравшая сторона (приглушение) |
| `--accent` | `#2563eb` | `#3b82f6` | Бренд/CTA, не несёт смысла направления |
| `--surface` / `--surface-2` | `#ffffff` / `#f8fafc` | `#0f172a` / `#1e293b` | Фон карточки / вложенный блок |
| `--border` | `#e2e8f0` | `#334155` | Разделители |
| `--text` / `--text-muted` | `#0f172a` / `#64748b` | `#f1f5f9` / `#94a3b8` | Текст / вторичный |

Правило: **зелёный/красный — только направленные**. Статичные элементы (теги, кнопки навигации) — нейтральные/бренд. Не использовать зелёный для «успех-тоста» и красный для «ошибки» теми же токенами — завести отдельные `--state-success/--state-error`, чтобы не путать «убыток» с «ошибкой формы».

**Доступность по цвету:** направление **никогда не кодируется только цветом** — всегда дублируется знаком (`+`/`−`), стрелкой (▲/▼) или текстом. Контраст текста на фоне ≥ 4.5:1, бейджей ≥ 3:1.

**Типографика:**

| Токен | Размер / вес | Применение |
|-------|--------------|------------|
| `--font-num` | tabular-nums, моноширинные цифры | **Все числа** (цены, P&L, объёмы) — чтобы не «прыгали» при live-обновлении |
| `--t-display` | 28–34px / 700 | Крупный `%` на детали рынка |
| `--t-price` | 18–20px / 600 | `%` на карточке, цена на кнопке исхода |
| `--t-body` | 14px / 400 | Основной текст |
| `--t-label` | 12px / 500, uppercase, letter-spacing | Лейблы строк тикета/чека |

`font-variant-numeric: tabular-nums` обязателен на всех числовых элементах (живые котировки иначе дёргают layout).

**Отступы (шкала 4px):** `--space-1:4 / -2:8 / -3:12 / -4:16 / -6:24 / -8:32`. Скругления: `--radius-sm:8 / -md:12 / -lg:16` (карточка — `lg`, кнопки — `md`, бейджи — `full`). Тени: только `--shadow-card` (hover-приподнятие карточки) и `--shadow-pop` (тикет/поповер).

### 5.3 Состояния (обязательны для каждого data-компонента)

Каждый компонент, который грузит данные или отражает рынок, должен явно поддерживать **пять состояний**. Это не опция — это контракт пропса `state`.

| Состояние | Визуал | Правило |
|-----------|--------|---------|
| `loading` | Skeleton-плейсхолдер той же геометрии (не спиннер по центру) | Никакого layout-shift при подгрузке; высота резервируется заранее |
| `empty` | Иллюстрация + 1 строка + опц. CTA | Тексты честные: «Сделок пока нет», а не фейковый тренд из 2 точек (см. `R12`/мастер-план §3.1). Убрать «фейковые посты убраны» из прод-копий |
| `error` | Короткий текст + кнопка «Повторить» | Не молчать (см. `logout().catch(()=>{})` в `C8`) |
| `resolved` | Баннер «Решено: ДА», проигравшая сторона → `--dir-flat`, торговля заблокирована | Кнопка «Получить выигрыш» = `доли × 1` (или авто-начисление + косметика) |
| `canceled` | Баннер «Отменён — возврат по себестоимости» | Все CTA-покупки убраны |

Промежуточные статусы рынка из мастер-плана (`DRAFT → OPEN → CLOSED → RESOLVING → RESOLVED → CANCELED`) маппятся в бейдж статуса: `closed` → «Ожидает расчёта», `resolving` → «Идёт расчёт».

### 5.4 Набор переиспользуемых компонентов (с пропсами)

Каноничный набор, на котором собираются все экраны. Пропсы — TypeScript-сигнатуры. Числовые поля — в `micro`/`cents`, форматирование внутри через слой 5.1.

**`MarketCard`** — карточка рынка в сетке/ленте.
```ts
{
  market: Market;            // вопрос, category(key), status, image
  yesPriceCents: number;     // 0..100, NO = 100 - yes
  delta24hCents: number;     // знаковое, для направления цвета
  history: HistoryPoint[];   // для Sparkline (только YES)
  volumeMicro: number;
  closeDate: string;
  commentCount?: number;
  bookmarked?: boolean;      // если функции нет — НЕ рендерить иконку (никаких мёртвых контролов)
  onBuy: (outcome: Outcome) => void;  // ведёт в предзаполненный тикет
  state: ComponentState;
}
```
Анатомия (источники `R8`/`R12`): иконка + вопрос, крупный `%` YES (`--t-price`), `Sparkline`, две `OutcomeButton` (зелёная «Купить Да 72¢» / красная «Купить Нет 28¢»), футер: объём + опц. счётчик комментариев + дата. Мульти-исход — строки `OutcomeRow` (см. ниже).

**`Sparkline`** — безосевой мини-график вероятности.
```ts
{ points: HistoryPoint[]; direction: 'up'|'down'|'flat'; height?: number; }
```
Только линия YES, цвет по `direction`. Пустой ряд → плоская линия, не фейк-тренд.

**`PriceBadge` / `OutcomeButton`** — цена исхода как кнопка (ключевой паттерн Polymarket, цена прямо на кнопке).
```ts
// PriceBadge — read-only
{ outcome: Outcome; cents: number; displayMode: 'percent'|'cents'|'american'|'decimal'; size: 'sm'|'md'|'lg'; }
// OutcomeButton — кликабельная
{ outcome: Outcome; cents: number; selected?: boolean; onClick: () => void; disabled?: boolean; }
```
Цвет: YES → `--yes`, NO → `--no`. `displayMode` поддерживает переключатель формата (`%` / `¢` / American / Decimal) — снижает порог для беттинг-аудитории (`R8`).

**`OutcomeRow`** — строка исхода для мульти-исходных событий.
```ts
{ label: string; cents: number; sparkline?: HistoryPoint[]; onBuyYes: ()=>void; onBuyNo: ()=>void; }
```
Каждый исход — своя строка со своим `%` и кнопками Да/Нет (`R7`/`R8`). Сумма всех YES ≈ 100%.

**`TradeTicket`** — sticky-тикет покупки/продажи (двигатель понятности, чинит D7).
```ts
{
  market: Market;
  side: 'BUY'|'SELL';
  outcome: Outcome;
  mode: 'spend'|'shares';        // BUY=spend(поинты), SELL=shares(доли) — без молчаливого сдвига смысла
  amount: number;
  quote: TradeQuote | null;      // из POST /quote: shares, cost, avgPriceCents, priceImpactCents, toWin, returnPercent
  balanceMicro: number;
  position?: ViewerPosition;
  onChange / onSubmit / onPreset; // пресеты +1/+10/+100/Макс
  state: ComponentState;
}
```
Структура (источники `R7`/`R12`): тоггл Купить/Продать; `OutcomeButton` Да/Нет; ввод с чипами `+1/+10/+100/Макс(=баланс)`; `PayoutCheck` (живой чек); жирная строка «Выиграешь: X»; строка проскальзывания (`maxPriceCents`); шаг подтверждения; блокировка BUY при `amount > balance`. SELL переключает ввод на доли + кнопка «Продать всё».

**`PayoutCheck`** — расчётный чек ордера (берёт всё из `TradeQuote`, который уже богат в `api.ts`).
```ts
{ shares: number; avgPriceCents: number; costMicro: number; feeMicro: number;
  toWinMicro: number; returnPercent: number; priceImpactCents: number; }
```
Строки: **Доли**, **Средняя цена (¢)**, **Влияние на цену**, **Комиссия** (скрыть при 0), **Потенциальный выигрыш** (поинты + `+%`). «Выиграешь» — самый заметный лейбл (мотивирующий, `R7`).

**`PnlBadge`** — направленный бейдж прибыли/убытка.


**`PositionsTable`** — таблица позиций (портфель).
```ts
{ positions: PortfolioPosition[]; groupBy?: 'category'|'status'; }
// колонки: рынок | доли | средняя ¢ | текущая ¢ | стоимость (pts) | P&L (PnlBadge)
```
Группировка по категориям/статусу (open vs resolved-к-получению), как портфель Polymarket по доменам (`R12`).

**`ResolutionBanner`** — баннер резолюции/отмены.
```ts
{ kind: 'resolved'|'canceled'|'resolving'|'closed'; winningOutcome?: Outcome;
  sourceUrl?: string; note?: string; redeemableMicro?: number; onRedeem?: ()=>void; }
```
Resolved → «Решено: ДА» + кнопка «Получить выигрыш»; canceled → «Возврат по себестоимости»; resolving/closed → «Ожидает расчёта».

**`RulesBlock`** — правила резолюции (Rules-first, `R7`).
```ts
{ sourceUrl: string; closeDate: string; edgeCases: string; }
```
Три обязательных элемента: источник (ссылка), дата закрытия + таймзона, крайние случаи. Без них рынок не публикуется (мастер-план §5.1).

**`RangeChart`** — основной график вероятности.
```ts
{ series: HistoryPoint[]; range: '1H'|'6H'|'1D'|'1W'|'1M'|'ALL';
  onRangeChange: (r)=>void; volume?: VolumePoint[]; multiOutcome?: OutcomeSeries[]; }
```
Селектор диапазона `1H/6H/1D/1W/1M/ALL`, цвет линии по направлению окна, столбики объёма, привязанный тултип с `%` и датой (детали в мастер-плане §3.2).

### 5.5 Доступность и мобильная адаптация

**Доступность:**
- Направление — **знак + цвет + текст** (см. 5.2); ничего «только цветом».
- Все интерактивные элементы — `aria-label` (в `i18n` уже есть `increaseAmount`/`decreaseAmount`/`showPassword` и т.п. — продолжить паттерн), видимый `:focus-visible`, тач-таргет ≥ 44×44px.
- Живые числа — `aria-live="polite"` на котировке, но не на каждом тике (троттлинг), иначе скринридер захлёбывается.
- `prefers-reduced-motion` → отключить анимацию линии графика и приподнятие карточек.

**Мобайл (источники `R12` — для аудитории это главный, иногда единственный канал):**
- Тикет → закреплённый снизу `bottom-sheet` / sticky CTA; «тяжёлые» элементы (стакан/влияние на цену, объёмные гистограммы) уходят глубже, наверх — `%`/график/кнопки.
- График: **горизонтальный свайп = скраб/пан графика, вертикальный = скролл страницы** (разделение осей жестов — критично для качества).
- Двойной формат на карточке: `67% / 67¢` (вероятность новичку, центы трейдеру).
- Кнопки Да/Нет прямо в карточке → покупка в 1–2 тапа из ленты.
- Категории — горизонтальный скролл-ряд чипов, переключение одним тапом.

### 5.6 Стабильные ключи категорий (отвязка таксономии от языка)

Сейчас таксономия завязана на русские строки как канонические ключи (`categoryValues`, `ALL_CATEGORY = 'Все'`, `Market.category: string` хранит русскую строку — диагноз `C8`). Любое переименование на сервере ломает перевод; EN-fallback показывает русскую строку. **Чиним: хранить ключ, рисовать лейбл.**

**Новая модель:**
```ts
type CategoryKey = 'all'|'general'|'politics'|'crypto'|'sports'|'finance'|'geopolitics'|'tech';

const CATEGORY_LABELS: Record<Language, Record<CategoryKey, string>> = {
  ru: { all:'Все', politics:'Политика', crypto:'Криптовалюта', sports:'Спорт',
        finance:'Финансы', geopolitics:'Геополитика', tech:'Технологии', general:'Общее' },
  en: { all:'All', politics:'Politics', crypto:'Crypto', sports:'Sports',
        finance:'Finance', geopolitics:'Geopolitics', tech:'Technology', general:'General' },
};
```

| Правило | Было | Стало |
|---------|------|-------|
| Хранение | `category: 'Политика'` (RU-строка) | `category: 'politics'` (стабильный ключ) |
| Сентинел «все» | `ALL_CATEGORY = 'Все'` | `'all'` |
| Источник списка | дубль `categoryValues` / `navCategoryValues`, расходятся между `CreateMarket` и `Navbar` | **один** `CATEGORY_KEYS`, оба экрана читают его |
| Отображение | `getCategoryLabel` fallback → сам ключ (русская строка в EN) | `CATEGORY_LABELS[lang][key]`, fallback → `key` (нейтральный slug, не RU) |
| URL/SEO | — | slug = ключ (`/category/politics`), как event/market slug в `R8` |

Миграция: одноразовый бэкфилл `markets.category` RU-строка → ключ по словарю. На будущее — допустить **массив тегов** и иерархию (Polymarket: `Finance · IPO · Stocks`), но это P3; ключ-таксономия — фундамент для них.

## 6. Резюме, дорожная карта и приоритетный бэклог

### 6.1 Резюме для руководителя

Хорошая новость: ядро уже почти на месте. Экономический фундамент Legio **уже переписан на LMSR и реально подключён** — `placeTrade` исполняет сделки через `server/lib/lmsr.js`, инвариант `YES+NO=100` держится математически (446 896 ассертов в тестах проходят), победителям **реально платят** при резолюции, а двойная бухгалтерия (`ledger`) пишется на каждой операции под защитой Postgres-транзакций с `FOR UPDATE`. То есть болезни D1–D3 из мастер-плана на бэкенде по сути вылечены — это серьёзный скачок относительно исходного диагноза «слив очков с графиком».

Плохая новость: **вся эта корректная экономика почти не видна пользователю и местами недостроена**. Тикет путает единицы (BUY в поинтах, SELL в долях, два поля «Получишь»), график **фабрикуется из seed** (не отражает реальные сделки и не имеет селектора диапазона), нет страниц портфеля и лидерборда, нет UI-выбора выигравшего исхода для мульти-рынков (а на Postgres мульти вообще не торгуются), резолюция не показывает превью выплат и не передаёт заметку/источник, нет проверяемого глобального инварианта сохранения средств, а бренд на десктопе всё ещё «Polymarket». Переработка по фазам ниже закрывает оставшиеся бэкенд-дыры P0 и затем делает экономику **понятной, липкой и масштабируемой** через UI — в строгом порядке, не украшая до того, как приземлится фундамент.

> Сверка с `docs/REDESIGN_PLAN_RU.md`: этот раздел не отменяет §6 плана, а уплотняет его и пересчитывает приоритеты с учётом аудита кода — часть задач P0 из плана (lmsr.js, ledger, schema, базовый `placeTrade`/`resolve`) **уже сделана**, поэтому здесь P0 сводится к закрытию конкретных оставшихся дыр, а вес смещён на UI-фазы P1–P2.

### 6.2 Фазовая дорожная карта

#### P0 — Достроить экономический фундамент (≈1–1.5 недели; меньше, чем в исходном плане, т.к. ядро готово)

**Цель:** закрыть оставшиеся дыры сохранения и резолюции, чтобы ни один сценарий не терял средства и мульти-рынки были торгуемы и резолвимы.

| Задача | Что сделать | Файлы |
|---|---|---|
| Мульти на Postgres | Убрать заглушку `MULTI_PG_UNSUPPORTED`; реализовать PG-ветку мульти-исполнения через уже готовые `calculateMultiFill`/`applyYesShares` | `server/index.js:1857`, `:499` |
| Валидация выигравшего исхода | В `resolveMarket` проверять, что `winningOutcome` существует в `outcomesDef`; иначе `400`, а не молчаливое сжигание всех позиций | `server/index.js:2005`, `:2656` |
| Глобальный инвариант сохранения | Эндпоинт/скрипт reconciliation: `SUM(delta) GROUP BY account` по всему леджеру == 0; материализовать/сидировать счёт `house`; CI-проверка инварианта | `server/index.js:1011`, `:2134`, `:2143` |
| JSON-путь | Запретить JSON-запись для торгов в проде (Postgres-only) либо in-process мьютекс — закрыть double-spend в фолбэке | `server/index.js:1896` |

**Критерии приёмки:**
- Мульти-рынок на Postgres торгуется и резолвится корректно; `displayedPriceMulti` сумма == 100.
- Резолюция несуществующим исходом отклоняется; `Δ Σ балансов == Σ выигрышных долей`.
- `SUM(ledger.delta) == 0` глобально и per-account сходится; reconciliation проходит в CI.
- Параллельные сделки в фолбэке не теряют обновления.

#### P1 — Понятный тикет + реальные графики + единицы (≈2.5–3 недели; самая высокая UX-отдача)

**Цель:** пользователь на любом экране видит одни и те же три числа — **цена/% · сколько плачу · сколько выиграю** — и график отражает реальную динамику.

Ключевые задачи:
- **Тикет** (`MarketDetail.tsx`, `TradePanel`): убрать двойное «Получишь» в SELL (нижняя строка → «У тебя долей»), починить конфликт дробных чипов со степпером и `step=1`/`min=1`, заменить гостевой CTA «голосовать» (`loginToVote`) на «войти, чтобы торговать», добавить кнопку **«Получить выигрыш»**/сумму выплаты в resolved-состоянии (сейчас только баннер-заглушка, `:172-190`).
- **История цен (бэкенд)**: переписать `buildHistory`/`buildMultiHistory` на реальный ряд `{t,p,v}` с бакетированием + forward-fill из `yes_price_after_cents`/`prices_after`; добавить параметр `?range=1H|6H|1D|1W|1M|ALL` (по образцу `prices-history` Polymarket: окно → fidelity); поднять кап с 80 до ~300–500 сделок; ввести персистентную серию или хотя бы авторитетный ресемплинг.
- **График (фронтенд)** (`PriceChart.tsx`): добавить отсутствующий **селектор диапазона** (главный визуальный пробел), объём в тултипе/подграфике, интерактивную легенду-фильтр; сохранить уже хороший самодельный hover (кэш семплов + бинпоиск) и ось времени.
- **Карточки**: заменить статический gauge на спарклайн из истории + цвет/дельта по знаку `oneDayPriceChange`-аналога; оживить или убрать мёртвые иконки (`Gift`, `Bookmark`).
- **Единицы и терминология**: единый форматтер (убрать `$` из маркетинговых строк, зафиксировать «поинты/¢ = %»); вычистить остатки «vote»/«голосование» (`api.vote`, `voteTitle`, `i18n`); починить бренд (десктоп-навбар «Polymarket» → «Legio», `Navbar.tsx:134`).
- **404-маршрут** в `App.tsx`.

**Критерии приёмки:**
- Quote == fill; в SELL нет двух полей «Получишь»; дробные доли не схлопываются степпером.
- График строится из реальных таймстемпов сделок; переключение 1H/6H/1D/1W/1M/ALL перезапрашивает и перерисовывает; на закрытых рынках корректная деградация гранулярности.
- Нигде нет слова «голосование»; во всём UI одна единица; бренд «Legio» консистентен на desktop/mobile.

#### P2 — Портфель + социальный слой (≈2–3 недели; удержание)

**Цель:** трейдер видит свои позиции и P&L по всем рынкам и сравнивает себя с другими.

Ключевые задачи:
- `GET /api/portfolio` + страница `/portfolio` (маршрута сейчас нет): стоимость портфеля, кэш, общий/нереализованный P&L, таблица позиций open/resolved-к-получению, личная история сделок (личного trade-history эндпоинта тоже нет).
- Расширить `MarketViewerPosition` (`api.ts:43`) до `currentValue/unrealizedPnl/costBasis`; читать леджер для аудита (сейчас write-only).
- `GET /api/leaderboard?metric=pnl|volume&window=` + страница `/leaderboard` + публичные профили; глобальная `/activity`; рабочий watchlist (обещан в i18n, не реализован).
- Серверные сортировка/фильтр/пагинация ленты (`/api/markets` сейчас игнорирует query, всё клиентское) + индексы `markets(status)`, `markets(category)`; оживить мёртвую кнопку фильтров и вкладки Trends/New; Top Holders на детали.

**Критерии приёмки:**
- `/portfolio` показывает агрегированный P&L, совпадающий с суммой по позициям; resolved-выигрыши получаются.
- Лидерборд считается из леджера/агрегатов и сходится с reconciliation; пагинация ленты работает на каталоге > 1000 рынков.

#### P3 — Мульти-исход в UI + диспуты + масштаб (≈3–4 недели)

**Цель:** категориальные рынки доступны через продукт целиком, резолюция прозрачна и оспорима, каталог масштабируется.

Ключевые задачи:
- **Создание мульти через UI**: `CreateMarket.tsx` сейчас **никогда не шлёт `outcomes`** — категориальный рынок через форму создать нельзя, хотя бэкенд это умеет. Добавить отправку `outcomes`, превью N-исходов, выбор типа.
- **Резолюция мульти в UI**: кнопки в `AdminPage.tsx:661/668` зашиты на YES/NO — добавить пикер произвольного выигравшего исхода для `market_type='multi'`; превью выплат (число затронутых позиций, сумма); подключить уже готовый, но не передаваемый канал `note`/источник (`api.ts:232/239` vs `AdminPage.tsx:253/273`).
- **Событийная модель**: таблица `events` (зонтик над связанными рынками) + slug-и; мультилинейный график события с легендой.
- **Лёгкий диспут** (UMA без крипты): фиксированное окно ревью между предложением и финализацией, малый возвратный стейк, публичная неизменяемая запись резолюции; разделение роли `resolver` от `admin` (сейчас любой админ резолвит свои же рынки без аудит-лога); шаблон правил из 3 частей (источник-URL + дата с TZ + крайние случаи) с кодировкой исходов p1/p2/p3(50-50)/p4(too-early).
- Админский аудит-лог (роли/баланс/статус/удаление сейчас не логируются); вывод `resolved_by/at/note` в UI.

**Критерии приёмки:**
- Категориальный рынок создаётся и резолвится произвольным исходом полностью через UI.
- Резолюция показывает превью выплат и пишет источник/заметку; есть публичная запись и окно диспута; роль резолвера отделена; админские действия логируются.

> P4 (off-chain CLOB + реальные taker-комиссии + подключаемый оракул) и P5 (реальные деньги/USDC) остаются опциональными эндшпилями из мастер-плана — LMSR остаётся всегда-включённым контрагентом-фоллбэком, леджер и экономика к подмене «очки → деньги» уже готовы.
