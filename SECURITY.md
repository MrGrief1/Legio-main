# Безопасность Legio

Документ описывает, что уже защищено в коде, и что нужно один раз настроить в Railway вручную.

## Часть 1. Что нужно сделать в Railway (вручную)

Эти шаги нельзя выполнить из кода — переменные задаются в панели Railway.

Откройте сервис в Railway → вкладка **Variables** → добавьте переменные ниже → **Deploy**.

### Обязательно

| Переменная | Значение | Зачем |
|---|---|---|
| `SECRET_KEY` | случайные 128 hex-символов (см. команду ниже) | Подпись токенов входа. Без неё сервер не запустится. Если ключ утечёт — замените его, это разлогинит всех и обнулит украденные токены. |
| `NODE_ENV` | `production` | Включает HSTS, отключает bootstrap-админа, включает строгий CORS. В `Dockerfile` уже задано — проверьте, что не переопределено в Variables. |

Сгенерировать `SECRET_KEY`:

```bash
node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
```

### Рекомендуется

| Переменная | Значение | Зачем |
|---|---|---|
| `JWT_EXPIRES_IN` | `7d` (или `24h`, если хотите строже) | Срок жизни сессии. Токены лежат в localStorage браузера; досрочно их гасит смена или сброс пароля (см. «Отзыв сессий»). |
| `BCRYPT_ROUNDS` | `12` | Стоимость хеширования пароля. Замедляет перебор украденной базы. |
| `ALLOWED_ORIGINS` | пусто, либо `https://legio.news,https://www.legio.news` | Кто ещё может обращаться к API из браузера. Фронтенд отдаётся тем же процессом, поэтому он same-origin и в списке не нужен. |
| `ALLOW_BOOTSTRAP_ADMIN` | `false` | Иначе первый зарегистрировавшийся получает роль админа. |
| `INITIAL_ADMIN_EMAIL` | ваш логин администратора | Единственный способ получить админа из окружения: аккаунт создаётся при старте, если его нет, и получает роль admin. |
| `INITIAL_ADMIN_PASSWORD` | пусто после первого входа | Задаёт пароль этого аккаунта, пока переменная присутствует. Уберите её, иначе каждый деплой возвращает пароль из настроек. |
| `RESEND_API_KEY` | ключ Resend | Письма с одноразовыми кодами. Без него не работают регистрация, вход по коду и восстановление пароля. |
| `ALLOW_UNSENT_CODES` | не задавать | В production включает печать кодов в лог вместо письма. Код в логах — это код, доступный всем, у кого есть логи. |
| `VISITOR_ID_HASH_SALT` | отдельная случайная строка | Соль для хеша посетителя в статистике. По умолчанию берётся `SECRET_KEY` — отдельное значение лучше. |

### Сохранность данных (важно)

| Переменная | Значение | Зачем |
|---|---|---|
| `UPLOADS_DIR` | не задавать (или `/app/data/uploads`) | Куда складывать загруженные файлы. По умолчанию теперь берётся папка рядом с базой, то есть на volume. |
| `MONTHLY_PRIZE_POINTS` | `5000` | Сколько баллов начисляется призёру месяца. |

**Что было сломано:** загруженные аватары писались в `/app/uploads`, а volume у Railway смонтирован только на `/app/data`. Всё вне volume — это временный слой контейнера, который стирается при каждом деплое. База при этом продолжала ссылаться на `/uploads/123.png`, файла уже не было, и аватар откатывался на инициалы. Это и есть «сохранил инфо о себе, а всё сбросилось».

Текст профиля (имя, био, дата рождения) не терялся — он лежит в SQLite на volume; исчезали именно файлы.

**После деплоя:** новые загрузки сохраняются. Аватары, загруженные ранее, восстановить нельзя — файлы уже удалены прошлыми деплоями, их нужно загрузить заново. Файлы, которые ещё лежат в старой папке, переносятся на volume автоматически при первом запуске.

Проверьте, что volume смонтирован на `/app/data`, и что в логах при старте есть строка:

```
Uploads path: /app/data/uploads
```

### Проверить после деплоя

1. **Секреты не в Git.** `.env` в `.gitignore`; в репозитории только `.env.example` с заглушками. Проверено — реальных ключей в истории нет.
2. **Заголовки.** Замените домен и выполните:

```bash
curl -sI https://ваш-домен/api/leaders | grep -iE "content-security-policy|strict-transport|x-frame|x-content-type"
```

Ожидается `script-src 'self'` без `unsafe-inline`, `frame-ancestors 'none'`, `Strict-Transport-Security`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`.

3. **Volume для базы.** База — SQLite. Убедитесь, что подключён persistent volume на `/app/data`, иначе данные теряются при каждом деплое.
4. **Смените пароль администратора**, если он когда-либо вводился на не-HTTPS адресе или переиспользован с другого сайта.

### Чего в проекте нет (осознанные ограничения)

- **Отзыв одной конкретной сессии** — нет. Отзываются либо все сразу (смена или сброс пароля, смена почты), либо по истечении `JWT_EXPIRES_IN`. Списка активных устройств нет.
- **Второй фактор помимо почты** — нет. TOTP-приложения и коды восстановления не поддерживаются, а почта одновременно служит и вторым фактором, и каналом восстановления: доступ к ящику — это доступ к аккаунту.
- **Обязательный второй фактор** — нет. Вход по коду включает сам пользователь; администраторам он не навязывается.
- **Логи аудита действий админов** — нет. Начисления баллов пишутся в `points_history`, смены ролей не логируются.

## Часть 2. Что уже сделано в коде

### Аутентификация и сессии

- Токены входа теперь имеют срок жизни (`JWT_EXPIRES_IN`, по умолчанию 7 дней). Раньше `jwt.sign` вызывался без `expiresIn` — выданный токен был вечным, и его нельзя было обесценить даже сменой пароля.
- Токены без claim `exp` отклоняются. Это выводит из обращения все ранее выданные бессрочные токены — **все пользователи войдут заново один раз**. Фронтенд обрабатывает это сам: при ошибке `/auth/me` токен удаляется из localStorage.
- Алгоритм подписи зафиксирован (`HS256`), поэтому подделка с `alg: none` не проходит.
- Стоимость bcrypt поднята с 10 до 12. Старые хеши продолжают работать — стоимость записана внутри каждого хеша.
- Ограничение на смену пароля/почты: 10 попыток в час с одного IP.

### Одноразовые коды на почту

- Регистрация двухшаговая: аккаунт создаётся только после ввода кода, до этого заявка живёт в таблице `auth_codes`. Заявка опознаётся по непредсказуемому `challengeId`, а не по адресу — иначе повторный запрос регистрации на чужой адрес подменял бы данные заявки, включая хеш пароля.
- Вход по коду (второй фактор) включается пользователем в настройках и подтверждается кодом — включить или выключить его одной украденной сессией нельзя.
- Смена пароля требует текущий пароль **и** код с почты; смена почты — код на старый адрес, затем на новый; привязка первой почты — текущий пароль плюс код на новый адрес.
- В базе хранится только SHA-256 кода, у кода 5 попыток и срок жизни 10–15 минут, между отправками пауза 60 секунд, а на все маршруты, отправляющие письма, действует отдельный лимит (`EMAIL_CODE_RATE_LIMIT_MAX`, 30 в час с IP).

### Отзыв сессий

- У каждого аккаунта есть поколение токенов (`users.token_version`), и токен несёт его в claim `tv`. Несовпадение — 401.
- Поколение увеличивается при смене пароля, сбросе пароля по коду и смене почты. То есть украденный токен перестаёт работать в тот момент, когда владелец меняет пароль, а не через 7 дней.
- Маршруты, которые отзывают сессии, возвращают новый токен — иначе смена пароля разлогинивала бы того, кто её только что выполнил.
- Токены, выданные до появления колонки, читаются как поколение `0` и остаются действующими: включение отзыва не требует одномоментного разлогина всех.

### Роли

- Роль администратора выдаётся только двумя путями: `INITIAL_ADMIN_EMAIL` (при старте) и повышение действующим админом через панель. Прежний механизм `FORCED_ADMIN_LOGINS` — молчаливое повышение любого, кто вошёл под логином из списка в переменных окружения — удалён.
- Нельзя снять роль администратора с последнего администратора. Раньше админ мог разжаловать сам себя и навсегда закрыть себе доступ к панели — восстановить это можно было только правкой базы.

### Заголовки и политика контента

- `script-src 'self'` — без `'unsafe-inline'` и без сторонних CDN. Это то, что превращает внедрённый `<script>` из «выполняется» в «заблокирован».
  - Чтобы это стало возможно: из `designe/index.html` удалён importmap на `aistudiocdn.com` (мёртвый код — Vite и так вбивает React в бандл, через importmap ничего не загружалось), а инлайновый скрипт вынесен в `designe/public/custom-elements-guard.js`.
  - **Не возвращайте инлайновые скрипты в `index.html`** — это потребует снова открыть `unsafe-inline` и обесценит защиту.
- Добавлены `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, `upgrade-insecure-requests`.
- `X-Frame-Options` изменён с `SAMEORIGIN` на `DENY`.
- HSTS на год с `includeSubDomains` и `preload` (только при `NODE_ENV=production`).
- `Referrer-Policy: strict-origin-when-cross-origin`.
- Убран устаревший `X-XSS-Protection` — в современных браузерах он не действует, а в старых сам был источником уязвимостей.
- CSP задаётся в одном месте: у helmet она отключена, чтобы две политики не конфликтовали.

### CORS

- В production при пустом `ALLOWED_ORIGINS` разрешён только свой origin. Раньше пустое значение означало «разрешить любой домен» — вместе с `credentials: true` это лишняя открытая дверь.
- **Свой origin разрешён всегда**, независимо от списка. Это обязательно: Vite ставит атрибут `crossorigin` на теги бандла и стилей, поэтому браузер присылает заголовок `Origin` даже когда страница грузит свои же файлы. Без этого исключения сайт отдавал сам себе JSON с ошибкой вместо CSS и JS и открывался белым.
- Отказ реализован **отсутствием** заголовков `Access-Control-*`, а не исключением. Брошенная ошибка попадала в обработчик и превращалась в 500 — то есть политика доступа выглядела как поломка сервера. Теперь запрет применяет сам браузер, как и задумано в CORS.

Проверка (подставьте свой домен):

```bash
curl -sI -H "Origin: https://ваш-домен" https://ваш-домен/api/leaders | grep -i access-control-allow-origin
```

Должен вернуться ваш домен. Для чужого origin заголовка не будет — и это не должно быть ошибкой 500.

### Загрузка файлов

- `/uploads` отдаётся с `Content-Security-Policy: default-src 'none'; sandbox` и `nosniff`, то есть содержимое загруженного файла не может исполниться в контексте сайта.
- Отдача не «проваливается» в SPA: отсутствующий файл — это 404, а не `index.html`.
- Лимит загрузок: 40 файлов в час с одного IP (5 МБ каждый) — иначе один аккаунт мог забить volume.
- Отклонённый по типу файл теперь возвращает 400 с причиной вместо непрозрачного 500.

### Ответы об ошибках

- 32 обработчика возвращали клиенту `err.message` от SQLite — это выдаёт названия таблиц, колонок и ограничений. Теперь сообщение фиксированное, а полная ошибка пишется в лог сервера.
- Ошибки express сохраняют свой статус: слишком большое тело — 413, битый JSON — 400. Раньше и то и другое превращалось в 500, то есть клиенту сообщалось «наша вина, повторите», хотя повтор не помог бы.
- Неизвестный путь `/api/*` отвечает JSON-ом `404`, а не HTML-оболочкой SPA.

### Прочее

- Лимит JSON-тела: 10 МБ → 256 КБ (`JSON_BODY_LIMIT`). Ни один маршрут не принимает больше пары килобайт.
- Убран `console.log` на каждый показ страницы.
- Контейнер уже сбрасывает root и работает под пользователем `node` (`docker-entrypoint.sh`, `gosu`) — оставлено как есть.

## Часть 3. Проверка

Тесты в `server/test/api.hardening.test.js` фиксируют это поведение, чтобы его нельзя было случайно откатить:

```bash
cd server && npm test
```

Покрыто: отклонение бессрочного, истёкшего и `alg:none` токена; наличие `exp` у выдаваемого токена; защита последнего админа; состав заголовков безопасности; отсутствие деталей драйвера в ответах; 404 JSON-ом на `/api/*`; отклонение слишком большого тела.

`server/test/api.security.test.js` и `server/test/emailAuth.test.js` дополнительно фиксируют схему с кодами: вход со вторым фактором не выдаёт токен без кода, код одноразовый, смена пароля требует и пароль, и код, смена почты проходит только через оба адреса, ответ восстановления не раскрывает существование аккаунта, смена и сброс пароля отзывают прежние токены, а код регистрации действует только со своей заявкой.
